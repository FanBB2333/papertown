# 三个核心设计：检查点、用户带着模型走、产出可溯源

## 1. 三个设计和它们的关系

Papertown 的方法有三个核心设计，也是对外讲的三件事。

1. **硬检查点和软检查点**。硬的由确定性代码把关，不过就锁住下游并打回。软的由模型做语义巡检，给出契合、预警、偏离。已有，见 `research_loop_design.md`。
2. **用户带着模型走，不是模型带着用户走**。方向、重要的实验方法、实验安排、文档设计由用户提出和决定。模型做调研、核实、广泛读文献和执行这些苦活累活。要杜绝的做法是「模型提一个建议，用户说好，模型就去做」。
3. **所有产出可溯源**。每个实验结果、文章里的每段文字，都能沿一棵树从文章一层层对到最底层不可分的结果文件，并回答：哪一次实验、什么时候做的、怎么算出来的、是哪位员工在哪一次操作里写下的。每项内容有一个只在项目内可见的溯源标签，机制和 Git 相同。

三者连成一条链：

```
用户的决定  ──依据──▶  模型的工作（调研、任务、实验、写作）  ──产出──▶  结果文件、图表、文章
     ▲                         │                                        │
     └──── 待定的事（模型摆事实，用户写决定）                      溯源树（每一层都能往下查到底，往上查到决定）
硬检查点和软检查点守在工序的出口和迭代环上，其中两条硬规则守的就是这条链：方法有据、摆事实不带倾向。
```

本文档是第 2、3 个设计的落地方案，也是实现的依据。

## 2. 现状和差距

**决定权在模型手里。**

- 负责人的说明里写着「这个项目由你推进」「自己定方法」「你能定的直接定」（`agents.py` 的 `LEAD_GUIDE`）。方法草案由负责人写，还会改掉项目标题（`pipeline.py`）。
- 卡片上「要用户决定的」是负责人写的一句话，配「同意」「不同意」两个按钮（`cards.py`、`decisions.py`）。
- 用户的回答没有留成记录：问题答完就关掉，卡片上的选择只存在 `card.json.decided` 里，页面上 45 秒后消失。
- 用户给方向的途径只有立项的 idea、对话、画布任务和工作边界。方法、实验安排、文档设计没有用户可写的记录。
- 多数记录没有作者：`items`（工序产出）没有提交人，小助手代建的画布任务记成「你」。

**产出和操作之间没有记录。**

- Papertown 只读项目的 git，不记录任何一次改动是谁做的。
- 实验任务只存命令和目录，没有当时的代码版本，也不知道它写出了哪些文件。
- 结果表里的 `job_id` 是一段不校验的文字，卡片上的指标是负责人手写的文字。
- 文章里的表、图、数字和结果文件之间没有任何关联。唯一问到「主张有没有依据」的是一条软巡检，答案是一段话。
- 已有而能用上的：`jobs.submitted_by`、`agent_sessions`（会话属于哪位员工）、各 CLI 的回合结束通知（`hosted.hook`）、本地任务的 `result.json`。

## 3. 设计一：用户带着模型走

### 3.1 分工

| 谁 | 做什么 |
| --- | --- |
| 用户 | 定方向。定方法：要解决的问题、机制、baseline、数据集、指标。定实验安排：做哪些实验和消融、先后和取舍。定文档设计：文章讲什么故事、怎么组织、哪些结论写进去。 |
| 负责人和员工 | 调研和读文献，核实事实，把查到的东西摆给用户。照用户的决定实现、跑实验、写作。执行层面的细节自己定：怎么实现、先后顺序、排错。 |

模型遇到要用户定的事，只做一件事：把问题、查到的事实、可能的做法摆出来，等用户写下决定。它不给倾向，页面上也没有「同意」按钮。

### 3.2 决定

用户的决定是一等记录，叫**决定**，项目内编号 `D1`、`D2`……每条属于研究流程七项中的一项（`pipeline.MODULES`：概览、调研、代码仓库、实验、数据、论文、员工），和中控屏、研究回路用同一套分块。

- 只有用户能写。写入口只在用户的接口上，`/api/bridge` 下没有创建决定的接口。
- 内容是用户自己的话。来源有四种：`idea`（立项时的 idea，自动成为 `D1`，属于概览）、`written`（在「决定」页写下）、`answer`（回答一件待定的事时写下）、`chat`（用户在对话里说过的一句话，原文照录）。
- 不能改。要改就写一条新的取代旧的（旧的状态变 `replaced`），或者撤回（`withdrawn`）。记录都留着。
- 每条决定带着**材料**：模型为这件事准备的调研页、汇报、论文、文件。看得出苦活是谁干的。
- 每条决定下面列出**照它展开的工作**：任务、实验、工序产出、派活、溯源记录。

`chat` 来源的规则：模型不能替用户写决定，只能指向用户说过的话。`pt said "原话片段"` 在本项目里用户亲手发的消息（`agent_events` 里 `kind=user` 且 `origin` 为 `web` 或 `terminal`，以及用户对问题的回答）中找这段原文，找到就把那条消息的全文记成决定，找不到就拒绝。用户也能在对话里把自己的消息「记为决定」。

### 3.3 待定的事

模型把一件要定的事交给用户，用 `pt raise`，不用 `pt ask`：

```
pt raise "问题" --mod <分项> --fact "查到的事实" [--fact …] [--option "一种可能的做法"]… [--material <种类>:<引用>]…
```

- 存成一条 `reports`（`kind='ask'`），`data.matter = {mod, facts, options, materials}`，`choices` 为空，`act` 为空。
- 没有「推荐」字段，做法不分主次。
- **硬规则**（代码拒绝，不靠提示词）：问题、事实、做法里出现第一人称的倾向（「我建议」「建议你」「建议选」「推荐选」「我倾向」「我认为应该」「最好选」「I recommend」「I suggest」「I'd go with」）时拒绝，回一句「只写事实和可能的做法，倾向留给用户」。转述他人的建议（「原论文建议用 X」）照常通过。
- 用户只能用**写下决定**来回答。页面上列出事实和做法，点一种做法会把它的文字放进输入框，用户改成自己的话再定下来。写下后生成一条决定（来源 `answer`，连同当时摆出的事实和做法），问的人收到 `<decision id="D4" mod="exp">…</decision>`，负责人不是提问人时也收到一份。

`pt ask` 留给事务性的问题（哪台机器、账号、权限）。工作边界里「需要询问」的动作（启动员工、推进工序、提交任务）仍是「可以 / 不可以」，那是用户自己设的许可，不是研究上的决定，页面上归在「许可」里。

卡片的 `need_you` 不再配「同意」「不同意」。每一行只有一个输入框，用户写下的话成为一条决定（来源 `answer`，分项由服务端按当前工序取 `STAGE_MOD`，用户可改）。

### 3.4 工作的依据

模型做的每件要紧的事都注明依据的是哪条决定：

| 工作 | 写法 | 存在哪 |
| --- | --- | --- |
| 工序产出 | `pt output <工序> '{…, "basis": ["D3"]}'`，方法草案按项写：`"basis": {"problem": ["D2"], "mechanism": ["D3"], "baselines": ["D4"], "datasets": ["D4"], "metrics": ["D5"]}` | `items.body.basis`，另加 `items.agent_id` 记提交人 |
| 提交实验 | `pt submit <名字> --by D5 -- <命令>` | `jobs.basis` |
| 派活 | `pt tell <谁> "…" --by D5` | 这条消息的事件数据 `basis`，送达的文字末尾附上「依据：D5「前 40 字」」 |
| 登记溯源 | `pt prov add … --by D5` | `prov.made.basis` |

- 依据可以是决定（`D3`），也可以是用户在研究回路上亲手建的任务（`#t4`，任务本身就是用户派的事）。小助手代建的任务记 `created_by: "assistant"`，不能当依据。
- 服务端校验：编号存在、属于本项目、仍然有效。不满足时拒绝并列出有问题的编号。
- 没有依据的工作不拒绝，记为**无据**，在「决定」页上单列出来。

### 3.5 负责人和员工的说明

`LEAD_GUIDE` 里和决定权有关的句子换成下面的意思（最终文字照仓库的文字写法定稿）：

- 这个项目由用户带着你做。方向、方法、实验安排、文档设计由他定，写在「决定」里，`pt decided` 随时看。你做调研、核实、读文献和执行，把事实摆给他。
- 遇到要定的事，不替他定，也不给一个方案等他点头。用 `pt raise` 摆出问题、你查到的事实和可能的做法，等他写下决定。事实要有出处。
- 他在对话里已经说过怎么做的，用 `pt said "他的原话"` 把那句话记成决定，再照着做。
- 方法设计：先调研，把问题、机制、baseline、数据集、指标各有哪些做法、各自的事实查清楚，逐项 `pt raise`。他都写下决定后，你把这些决定整理成方法草案，`basis` 里按项注明依据。草案里不出现他没定过的东西。
- 实验：做哪些实验和消融照他的决定。派活和提交实验带上 `--by`。结果出来后汇报事实，下一步做什么仍然由他定。
- 写作：文章的故事和结构照他的决定。
- 执行层面的细节你定：怎么实现、先后顺序、排错。拿不准一件事算不算细节时，当成要他定的事。
- 汇报只写事实：进展、结果、问题、等他定的事。

员工的说明：要定的事告诉负责人，由负责人 `pt raise`。项目简报（`town.brief`）里新增一节「用户的决定」，按分项列出有效的决定。卡片说明里 `need_you` 的写法改成「等用户定的事，只写事情本身」，示例换掉。软巡检「实验方向」「实验设计」的提问改成对照用户的决定。

### 3.6 硬检查：方法有据

`checks.HARD` 在方法设计工序加一条 `basis`「方法有据」：方法草案的问题、机制、baseline、数据集、指标五项，各至少对应一条仍然有效的用户决定。数值是没有依据的项数，上限 0，属于阻断级，过了才能收尾方法设计。旧项目的方法草案没有 `basis` 字段且工序已完成的，这条不评（状态 `none`），不让旧项目变红。

### 3.7 页面

页面的总要求是美观和简洁：新增的内容不把项目页撑长，一屏里只有一个重点，次要信息进详情。具体的版式规则见 3.8。

**项目页（`/progress/<编号>`）**：

- 「待你决定」仍是一节，不拆成三个框。里面的条目按顺序排：待定的事、卡片上等你定的事、许可，各用一个小标签区分。待定的事默认只显示问题和一个输入框，事实、可能的做法、材料收在「查看事实」里展开。卡片上等你定的事一行一个输入框。许可保持原样。
- 「你的决定」和「溯源」各只占一行，放在负责人开关下面，样式是信息条：「决定 7 · 有据 12 · 无据 2」「溯源 表和图 3/5 · 数字 12/15 · 改过 2 · 操作 86」。点一行进入对应的整窗页面。项目页上不再为它们另起大节。

**决定页（`/progress/<编号>/decided`，整窗）**：

- 顶部一行：统计和「写下决定」按钮（弹层里选分项、写内容、可选「取代 D3」）。
- 主体是一列按时间倒序的决定，一条一行半：编号、分项、原文的前两行、时间。上方一排分项筛选（只列出有决定的分项，默认「全部」）。被取代和撤回的收在末尾的「已取代和撤回」里。
- 点一条在右侧展开详情（窄屏下整页）：原文全文、来源、当时摆出的事实和做法（来源是待定的事时）、材料、照它展开的工作（任务、实验、产出、派活、溯源记录，各能点到对应页面）、取代关系，以及「改写」「撤回」。
- 「无据的工作」是筛选里的最后一项，有才出现。

**对话**：用户自己发的消息上有「记为决定」。

**研究回路**：人类拍板节点列出待定的事并链接到项目页的输入框。任务节点和工序节点的详情显示依据。每个分块的资料卡显示该分项有效决定的数量。

**App**：项目页的待决事项按同样的顺序和小标签显示，新增「决定」页（列表、详情、写下决定、改写、撤回）。

### 3.8 版式规则

这两张页面和项目页上新增的内容都照这几条做，网页和 App 相同：

- **一屏一个重点**。列表是主体，统计只占一行，操作只留一个主按钮（「写下决定」「定下来」），其余操作进详情或菜单。
- **先少后多**。默认只显示判断所需的最少内容：编号、标题或前两行、时间。事实、材料、差异、会话编号这些点开才出现。
- **不套框**。列表项之间用留白和细分隔线，不给每一项加边框和底色，不在卡片里再放卡片。
- **颜色克制**。正文和次要信息两级灰度。强调色只用于主按钮和当前选中。状态色（通过、预警、受阻）只用于状态记号，并配图标或文字。
- **正常的不标**。只有需要注意的东西带记号。数量为零的统计项不显示。
- **空状态一句话**。暂无内容时写「暂无决定」这样的一句，外加一个能开始的按钮，不放插图和大段说明。
- **对齐现有页面**。字号、间距、圆角、分隔线、按钮都用项目页和研究回路已有的那一套，三种界面风格和深色模式下都检查。

## 4. 设计二：产出可溯源

### 4.1 三个概念

- **操作**：一位员工的一个回合，或一次任务，对项目文件造成的一组改动。每个操作是溯源库里的一次提交，记着谁、哪个会话、什么时候、改了哪些文件。
- **溯源记录**：一项内容和它的来历。内容可以是文章里的一段文字、一个中间产物文件、一个结果文件。来历包括它在哪个操作里产生、怎么来的、来自哪些更底层的记录、依据的是哪条决定。
- **溯源标签**：溯源记录的 7 位编号，由内容算出，只在这个项目里有意义。

溯源分两层，来源不同：

| 层 | 回答什么 | 怎么得到 |
| --- | --- | --- |
| 操作层 | 这一行是谁、在哪次操作里写下的 | **自动**。Papertown 在每个回合结束时给项目文件拍一次快照，用 `git blame` 就能把任何一行对到操作 |
| 依据层 | 这个数字、这张表来自哪些结果文件，那些文件又是哪次实验跑出来的 | 员工用 `pt prov add` **登记**，服务端校验文件存在、算出内容编号、补上操作和任务信息 |

### 4.2 溯源库和操作

每个项目在 Papertown 自己的数据目录里有一个裸仓库 `projects/<项目>/prov.git`。它用 `--git-dir=prov.git --work-tree=<根目录>` 给项目的根目录拍快照，项目自己的目录和 `.git` 一个字节都不写。根目录有两个：代码（`code`）和论文（`paper`），各占一条分支，各是一条线性历史。

快照里放什么：

- 根目录是 git 仓库时，取已跟踪的文件和未被忽略的未跟踪文件。不是仓库时遍历目录，跳过 `.git`、`node_modules`、`__pycache__`、`.venv`、`wandb`、`checkpoints`。
- 单个文件上限 1 MiB，超过的只记路径、大小和内容编号。
- 登记过的文件（`pt prov add` 提到的）从此每次都放，即使它被 `.gitignore` 忽略。结果文件通常就在被忽略的目录里。

什么时候拍：

| 时机（`trigger`） | 改动算谁的 |
| --- | --- |
| `turn`：一位员工的一个回合结束（Claude 的 `Stop`、Codex 的回合完成通知、Antigravity 和 Paseo 的状态从工作中变为空闲） | 这位员工 |
| `before`：一条消息送达员工之前 | 没有员工在这个根目录里工作时算「你或外部工具」，有则算正在工作的那些员工 |
| `submit`、`job`：提交实验时、任务结束时 | 同上。提交时的代码快照编号记在任务上，这就是「这次实验跑的是哪一版代码」 |
| `add`：登记溯源时 | 登记的员工 |
| `tick`、`manual`：巡检时、用户点「现在记一次」 | 同 `before` |
| `base`：第一次快照 | 「开始记录前已有」。根目录是 git 仓库时，这些行再用仓库自己的 `git blame` 给出提交、作者和日期 |

没有改动就不产生提交。同一个根目录的快照排队执行，间隔不小于 5 秒，在后台线程里做，不阻塞消息和通知。提交信息的尾注写明来历：

```
turn: 写作员工改了 2 个文件

Papertown-Agent: writer-line_3
Papertown-Role: writer
Papertown-Session: 0f3c…
Papertown-Trigger: turn
Papertown-Basis: D8
```

`Papertown-Basis` 取这位员工最近收到的那次派活的依据。

### 4.3 溯源记录和树

记录有四种：

| 种类 | 是什么 | 位置 |
| --- | --- | --- |
| `passage` 文字 | 文章里的一段：一张表、一张图、一句带数字的话、一段论述 | 论文根目录里的文件、行号范围和登记时的原文 |
| `artifact` 中间产物 | 由别的文件算出来的文件：汇总表、图、处理过的数据。也包括实验工序交的结果表 | 文件路径和登记时的内容编号，或工序产出的 id |
| `result` 结果文件 | 一次运行直接写出的文件，树的叶子，不可再分 | 文件路径、内容编号、任务 |
| `source` 外部来源 | 引用的论文、外部数据集 | `arxiv:` 编号、bib 键或路径 |

树从文章往下长：

```
文章
└─ sections/exp.tex · §4 Experiments
   ├─ 7c2e1a9  表 2 主结果（120–134 行）        写作员工 · 11-24 21:03 · 数字 8/8 对得上 · 依据 D8
   │  └─ 91ab03f  results/main_table.csv  中间产物   代码员工 · 11-24 20:40 · scripts/agg.py
   │     ├─ e11f2c0  outputs/run_a/result.json  结果文件   job_3fa2 · 18:02–19:40 · 代码版本 c0de12a · 依据 D5
   │     └─ e120b7d  outputs/run_b/result.json  结果文件   …
   └─ 其余文字：写作员工 42 行 · 开始记录前已有 310 行 · 你或外部工具 12 行
```

文章这一层自动得到：论文根目录里的每个 `.tex` 文件按 `\section`、`\subsection` 切开，登记过的文字挂在所在的小节下，没登记的文字按操作层汇总成「其余文字」。所以即使一条都没登记，树也不是空的。页面上，有登记记录的小节排在前面并展开，没有登记记录的小节合并成文件末尾的一行「其余 6 个小节」，点开才逐个列出，这样一打开看到的就是有来历可查的内容。

每条记录记着：标签、种类、标题、位置、登记时所在的操作、来历（时间、员工、岗位、模型、会话、做法 `how`、任务、依据）、来源（下一层的记录）。同一位置再次登记时，新记录取代旧记录，旧的留着。

### 4.4 员工怎么登记

```
pt prov                                  # 概况，以及文章里还没登记来源的表和图
pt prov add <目标> [--from <来源>]… [--how "命令或做法"] [--job <任务 id>] [--by D<n>] [--title "…"] [--note "…"]
pt prov show <标签>
```

- 目标：`paper/sections/exp.tex:120-134`（行号范围）、`paper/sections/exp.tex#tab:main`（LaTeX 标签，取它所在的浮动体的行）、`code/results/main.csv`，或相对员工工作目录的路径（服务端判断它在哪个根目录里）。
- 来源：已有的标签、文件路径（没登记过的当场登记）、`job:<任务 id>`、`cite:<bib 键>`、`arxiv:<编号>`。
- 种类由服务端判断：目标在论文里且带行号或标签是文字。目标是文件且带 `--job`、没有 `--from` 是结果文件。目标是文件且带 `--from` 是中间产物。
- 服务端做的事：先拍一次快照。校验文件和行号存在、任务存在。算内容编号。从登记的员工、它的会话和当时的操作填好来历。文件没有任务也没有来源时照样登记，标成「来历未登记」。

省事的写法：

- `pt submit <名字> --by D5 --out outputs/run_a/result.json -- <命令>`：任务成功结束后，`--out` 的文件自动登记成结果文件。任务目录里的 `result.json` 也自动登记。
- `pt output exp` 的每一行可以写 `"from": ["<标签、任务 id 或路径>"]`，服务端把结果表登记成中间产物并连好来源。原来不校验的 `job_id` 改为校验。

写作员工、代码员工的说明各加一段：写进文章的每张表、每张图、每句带数字的结论，写完就 `pt prov add` 登记来源。跑出来要用的结果文件，在提交时用 `--out` 报上。

### 4.5 核对

溯源记录不只是一张关系图，页面上每个节点都带着代码算出的核对结果：

- **内容是否和登记时一致**。文件类比较内容编号：`ok` 一致、`changed` 登记后改过、`missing` 文件没了。文字类在当前文件里找登记时的原文：`ok` 还在原处、`moved` 还在但行号变了、`changed` 已被改写。结果文件登记后被改动，这里立刻看得到，还能看前后差异，因为登记时的内容存在溯源库里。
- **数字是否对得上**。对有来源的文字，从登记的原文里取出数字，到它的来源（一直到叶子）的文本文件里找。按文字里的小数位数四舍五入比较，同时比较乘以 100 的值（比例和百分数）。每个数字给出对上或没对上，节点上显示「数字 7/8 对得上」。
- **来历是否完整**。结果文件有没有任务，任务有没有代码版本，中间产物有没有做法和来源。

这一版只显示核对结果，不拦工序。

### 4.6 页面

**溯源页（`/progress/<编号>/prov`，整窗）**：

- 顶部一行统计，信息条的样式：表和图 3/5 · 数字 12/15 · 改过 2 · 操作 86。
- 左边两个视图：「从文章往下」是 4.3 的树，叶子没有被文章用到的记录归在最后的「还没用到的结果」里。「操作记录」按时间列出每次操作：时间、谁、改了几个文件、增删行数。
- 树的每个节点只占一行：状态记号、标签、标题，行尾是谁和时间。别的都进右边的详情。状态正常的节点不加任何标记，只有改过、缺失、数字没对上、来历不全才显示记号，这样一眼看到的就是有问题的地方。
- 右边是选中节点的详情：标签、位置（能点到中控屏的论文或代码面板）、登记时的内容和现在的内容、差异、这次操作（员工、岗位、模型、会话、时间，能点到那段对话）、怎么来的（做法、任务、代码版本）、依据的决定（点到决定页）、核对结果、它的来源、哪些记录用到了它。
- 选中操作时：这次操作改的文件和每个文件的差异。

**项目页**上是 3.7 说的那一行信息条。**决定页**里每条决定的工作清单包含溯源记录。**中控屏**的数据面板里，每次运行显示它的结果文件标签和「用在文章 2 处」，论文面板加一个「溯源」入口打开当前文件所在的树。**App** 新增「溯源」页：树和节点详情，只读。

## 6. 接口

用户的接口：

- `GET /api/lines/{id}/decided` → `{decisions: [Decision], matters: [Matter], loose: [Work], stats: {total, active, anchored, loose}, mods: [{id, name}]}`
- `GET /api/lines/{id}/decided/{did}` → `Decision` 加 `work: {jobs, outputs, tells, tasks, prov}`
- `POST /api/lines/{id}/decided {text, mod, replaces?, matter?, need?, materials?}`：写下决定。`matter` 是待定的事的报告 id，`need` 是卡片上那一行的原文
- `POST /api/lines/{id}/decided/quote {event_id, mod}`：把用户自己的一条消息记为决定
- `POST /api/lines/{id}/decided/{did}/withdraw`
- `GET /api/lines/{id}/prov` → `{stats, files: [{path, title, sections: [{title, line, nodes: [id], rest: [{who, lines}]}]}], nodes: {id: Node}, loose: [id]}`
- `GET /api/lines/{id}/prov/nodes/{nid}` → `Node` 加 `now`（现在的内容）、`then`（登记时的内容）、`diff`。`used` 和 `history` 均为 `[{id, tag, title}]`。
- `GET /api/lines/{id}/prov/ops?root=&before=&limit=` → `[Op]`。`before` 接受时间或完整操作编号，连续翻页使用上页末尾的完整编号。`GET /api/lines/{id}/prov/ops/{op}` 返回操作详情，`files` 为 `[{path, added, removed, diff}]`。
- `GET /api/lines/{id}/prov/blame?root=paper&path=…` → `[{start, end, op, who, role, at, node, commit?, author?, date?}]`
- `POST /api/lines/{id}/prov/snap`：现在记一次，返回 `{code, paper}`，每个值是对应根目录的快照编号或 `null`。

```
Decision { id, n, mod, text, source, ref, state, replaces, replaced_by, materials: [{kind, ref, title}], matter, created_at, ended_at, counts: {jobs, outputs, tells, tasks, prov} }
Matter   { id: integer, agent, who, question, mod, facts: [string], options: [string], materials: [{kind, ref, title}], since }
Work     { kind: "job"|"output"|"tell"|"task"|"prov", id, title, who, at, basis: [string] }
Node     { id, tag, kind, title, root: "code"|"paper"|null, path, span: {start, end, text}|null, blob, op, state: "ok"|"moved"|"changed"|"missing",
           made: {at, agent, role, who, model, session, how, job: {id, name, command, node, cwd, status, started_at, ended_at, op}|null, basis: [string]},
           src: [id], numbers: [{text, ok, where}], gaps: [string], note, created_at }
Op       { id, short, root, ts, trigger, agent, role, who, session, basis: [string], files, added, removed, summary }
```

卡片的 `decisions`（`Decisions.gather`）：`kind` 增加 `matter`，带 `mod`、`facts`、`options_text`、`materials`，`options` 为空。`need` 的 `options` 为空。两者都带 `write: true`，表示只能用写下决定来回答。`POST /api/lines/{id}/decide` 和 `POST /api/reports/{id}/answer` 遇到这两种时，要求有文字，并走写下决定的同一条路径。

已有接口上新增的字段：

- 项目卡片（`GET /api/cards`、`GET /api/lines/{id}/card`、事件 `card`）：`decided: {total, active, anchored, loose, latest: [{id, n, mod, text}]}`（`latest` 是每个分项最新的一条有效决定），`prov: {floats: {total, tagged}, numbers: {total, ok}, changed, ops, recent: [Op]}`（`recent` 是最近三次操作）。
- 研究回路（`GET /api/lines/{id}/canvas`）：`decided: {<分项>: 有效决定数}`。任务节点和工序节点带 `basis: [string]`，任务节点带 `created_by`。人类拍板节点的条目里，待定的事的 `kind` 为 `matter`，带 `ask`（报告 id）。
- 数据面板（`GET /api/lines/{id}/data`）：`runs[]` 带 `prov: [{id, tag, path, state, used}]`，`used` 是文章里用到它的文字条数。
- 对话：用户消息的事件数据带 `decided: "D3"`（已记为决定时）。

员工的接口（`/api/bridge/{agent}` 之下，`pt` 的新命令）：`GET /decided`（`pt decided`）、`POST /raise`（`pt raise`）、`POST /said`（`pt said`）、`GET /prov`（`pt prov`）、`POST /prov`（`pt prov add`）、`GET /prov/{tag}`（`pt prov show`）。`/output`、`/jobs`、`/tell` 接受依据和 `outs`。

总线事件：`decided`（`line_id`、`id`）、`prov`（`line_id`、`op` 或 `node`）。待定的事沿用 `report` 和 `card`。

## 8. 测试

- 决定：只有用户接口能写。`D1` 的补写。取代和撤回。`pt said` 找得到和找不到原话。`pt raise` 的倾向拦截和转述放行。待定的事只能用文字回答，回答后生成决定并送达。`need_you` 同理。依据的校验。无据的统计。硬检查「方法有据」的通过、阻断和旧项目不评。

## 9. 这一版不做

- 底层结果文件禁止模型修改这类管理规则。这一版只做到看得见：改了就显示「登记后改过」。
- 用溯源的核对结果拦工序。之后可以把「表和图都登记了来源」「数字都对得上」做成硬检查。
- 论文编辑器里逐行的溯源标记。
- nvidb 远程任务的代码版本。nvidb 只读，这一版只记它给出的命令、机器、目录和时间。
- 把溯源库或标签推到项目自己的仓库。标签只在 Papertown 的这个项目里可见，文章源码里不写任何标签。
- 数字核对只比数值。同一个数碰巧出现在别的运行里时也会对上，所以它回答的是「来源里有没有这个数」，不回答「是不是该用这次运行」。之后把表里的每个格子绑定到结果文件里的具体字段。
- 复现（给定版本和环境重算一遍）。这一版回答出处，不回答能否重算。

## 10. 和已有系统的关系

调研见 `core_ideas_survey.md`（2026-11-26，18 个系统）。和设计直接有关的三点：

- 决定：已有系统里，人的位置多是给题目、挑模型的候选、或者对模型的计划点继续（Carl、Agent Laboratory、CodeScientist）。Denario 允许人直接写 idea 和方法，但是可选的。没有查到把方向、方法、实验安排、文档设计四类决定都设成「用户先写、模型后做」的公开流程。先让人写下判断再看模型意见，有随机实验支持它能减少错采，也有反例，宣传时照实说。
- 溯源：data-to-paper 已经做到正文数字经公式、表、输出文件连到代码行，这是对标的基线。ScientistOne 有不进终稿的内部证据标签，YouRA 给每次状态变更记时间和归属。Papertown 要做的是把三条记录接通：文章用了什么证据、哪次运行生成了证据、哪位员工的哪次操作写下了这段话，再往上接到用户的决定。
- 检查点：Curie、AutoResearchClaw、ScientistOne 都有局部的确定性门禁和语义审查。Papertown 的区别在于检查点守的是「决定、工作、产出」这条链，而不只是工程上的通过与否。

## 实现说明

### 决定和依据

- 决定的 `id`、`replaces` 和 `replaced_by` 使用 `dc_…`。在本项目的详情、取代和撤回请求中也可写 `D3`。工作依据使用项目内的 `D3`、`#t4`。写入、引用和撤回接口均返回决定详情。
- 独立写决定时填写 `mod`。回答时可省略或覆盖它。待定的事默认沿用提问的分项，卡片事项默认沿用当前工序的分项。决定列表里的 `Matter.id` 和画布里的 `ask` 是整数，卡片 `decisions[].id` 沿用字符串。卡片回答接口返回更新后的卡片，报告回答接口返回更新后的报告。卡片事项只有原文，用项目的 `/decide` 或 `/decided` 回答。拥有报告编号的待定的事也可用 `/reports/{id}/answer` 回答。
- `Decision.ref` 是字符串或空值。对话引用存事件编号，引用事务性回答存 `report:<编号>`，回答待定的事存报告编号，回答卡片事项存原文。同一来源重复引用会返回原决定。回答待定的事的 `matter` 保存当时的 `question`、`mod`、`facts`、`options` 和 `materials`。报告事件上的 `data.decided` 与对话事件一样使用 `D3`。
- 研究决定和文字回答由用户接口接收。员工的 `/said` 只能引用该项目已有的用户原文。匹配时先查项目内最近的匹配消息，再查用户亲自回答的报告。带附件的消息按用户输入的原文引用。工作边界许可沿用原有选项。
- 用户消息的事件数据可带 `user_text`，用于保存用户亲手输入的文字。`text` 继续保存送达内容，可包含服务端附加的附件列表或页面上下文。三个员工接口沿用命令行工具的文本回包，`GET /decided` 返回 `{text}`，`POST /raise` 返回 `{id, text}`，`POST /said` 返回 `{id, n, text}`。
- `decided_delivery` 随决定一起保存收件人，离线员工恢复后收到原文。卡片中持续出现的同一事项沿用内部标识，`decided_needs` 随决定一起登记回答。事项从卡片移除、后来再次提出时可重新回答。原有卡片点选记录仍按原格式读取。
- `anchored` 按有依据的工作逐件计数。同一件工作可以列在多条决定的详情中。取代或撤回后保留历史工作和原来的引用。缺少依据的实验、工序产出、派活和画布任务从 `decided_since` 起进入 `loose`。工序节点的 `basis` 取最近一次产出，方法草案的分项依据在该节点去重合并。任务和实验均可引用用户亲手建的任务。「方法有据」逐项核对有效的用户决定。
- 工序产出统计覆盖可用 `pt output` 提交的查重报告、方法草案、结果表、论文稿和审稿意见。系统生成的立项记录、编队记录和出厂包沿用原有的工序记录。旧画布的硬卡口打回单按回路属性认定，其他任务用小助手已完成的建节点记录核对创建者。
- 「方法有据」接入现有的硬卡口，默认 P0 阻断，缺项上限为零。项目已有的卡口设置和用户手动放行入口同样适用。
- 新项目的显示标题沿用用户立项时的原文摘要，方法草案的英文题目保存在产出里。旧数据中若 `lines.idea` 为空，补写的 D1 保留空文，避免将其他来源的标题归给用户。已有的项目创建时间优先保留。

### 操作和溯源记录

- 第 6 节的用户接口、卡片、运行记录、决定详情和总线事件已接入实际历史。每个根目录的第一次快照建立基线，包括已经存在的空目录。旧项目在首次触发或首次打开溯源树时建立基线。卡片列表读取已有历史。关闭 `[history] prov` 会停止新登记和快照，已有记录仍可查看。
- Git 操作集中在 `prov_git.py` 的白名单内。两个分支分别使用裸库内的 `index-code` 和 `index-paper`。项目启用分离索引时，Git 即使使用 `--no-optional-locks` 也可能刷新共享索引的修改时间。列文件时在裸库内临时复制项目的工作索引及其引用的共享索引，沿用 Git 对工作树和忽略规则的解析。读取项目提交和原始行归属时使用独立的空索引。
- 快照收录常规文件，跳过符号链接、特殊文件、Git 元数据和含员工凭据的 `.papertown`。单文件默认上限 1 MiB。超限文件流式计算 Git blob 编号，树中保存大小和编号。私有树用独立的条目类型区分指针和恰好写有相同文字的普通文件。每个根目录默认收录 50,000 个文件。已登记路径每次都收录，超过上限时仍保留。其余按路径排序填入剩余额度。常放清单按 `{code: [path], paper: [path]}` 写入 `prov.json`，数据库也保留已登记路径以便恢复。
- 同一根目录的实时触发按顺序在后台执行。触发时确定归属，轮到该请求时采集文件。如果两次采集之间有多人交错修改同一文件，操作记录能标明当时在场的员工，逐次落盘的作者无法再细分。多人共同归属时 `who` 列出岗位和员工编号，单值的 `agent`、`role`、`session` 为空，各人的信息写入提交尾注。派活依据取最近实际送达的消息。负责人在自己的管理目录收发消息和结束回合时均跳过根目录快照。
- 本地实验在提交时取得代码版本，再启动命令。负责人通过 bridge 提交的本地实验使用项目代码目录。成功完成后异步登记结果，重启时继续处理待登记的任务。任务目录里的文件以 `jobs/<任务编号>/result.json` 展示。工序结果表用实际产出编号作 `path`。这两类记录以及外部来源的 `root` 为 `null`，它们的内容或外部引用保存在私有存储中。任务引用优先连到该任务的结果文件，其次使用本地任务打印的结构化结果。只有任务信息时保留任务引用和缺项。nvidb 的 `made.job.op` 为 `null`，附加的 `made.job.cwd` 保留它报告的运行目录。
- 行号从 1 开始，含首尾两行。两个根目录嵌套时，相对位置归入最具体的根目录。两者相同时，行号、浮动体标签和写作员工的相对路径归入 `paper`，其余相对路径归入 `code`。显式前缀可指定根目录。表和图按 `table`、`figure` 及其带星号环境识别。有来源的文字覆盖浮动体中的行即计入 `floats.tagged`。`stats.changed` 统计当前记录中的 `changed`，其余状态在节点详情展示。数字以登记时的文字为准，`where` 是当前来源链中首次匹配的路径或 `null`。一般的核对按两个快照头及登记版本缓存。位于任务目录的独立结果还依据文件状态信息刷新。
- 节点和标签都在本项目内查找。同一内容首次取 Git blob 编号的前 7 位，碰撞时逐位加长。`used` 和 `history` 返回 `[{id, tag, title}]`。历史中的记录仍可直接打开，也能作为原有论文依据。运行的 `used` 按当前各篇论文中的文字记录去重，包含间接使用。
- `blame` 的 `op` 始终指向可打开的 Papertown 操作。可与项目基线提交对上的行额外带 `commit`、`author`、`date`，分别是项目自己的提交编号、作者和时间。基线创建时已有的未提交改动归入「开始记录前已有」。操作列表的 `before` 接受上一条的时间或完整操作编号。手动快照返回 `{code: 提交编号或 null, paper: 提交编号或 null}`，已有相同内容时返回当时的分支头。
- 员工的 `GET /prov` 返回 `{stats, unregistered: [{path, start, end, type, labels}]}`。`POST /prov` 的字段为 `target`、`from`、`how`、`job`、`basis`、`title`、`note`，返回 Node。`GET /prov/{tag}` 返回完整节点详情。实验工序的 `/output` 回执附加 `prov: {id, tag}`，供下一层直接引用。项目卡片的 `recent` 是最近三次操作。
- 样例只在新放入时导入预置历史。已有样例保留用户当前的文件。预制论文按历史时间导入数次修订，盲审项目中有论文表格、中间产物和任务结果的完整链，以及数字不符、改动、移动和缺失的实例。导入过程使用私有 Git 对象和模拟任务记录。

### 网页联调

- 项目页直接使用卡片接口的两组统计和待处理条目。研究问题和卡片事项各有一个输入框，做法只填入草稿。文字去掉首尾空白后才可提交。工作边界许可的「允许」「拒绝」是显示文案，提交时保留服务端选项值。原生许可仍提交布尔值。
- 决定详情把实验连到那次运行，把工序产出和任务连到对应的回路节点，把派活连到原消息，把溯源记录连到节点详情。用户消息带附件时只引用 `user_text`。已停止的对话也会接收决定变更。旧会话中没有身份或无法唯一匹配的消息保留为可读记录。
- 论文树先展开有登记记录的小节，再按文件折叠其余小节。窄屏将员工和时间放在标题下。中控屏的结果文件标签和论文入口打开同一份溯源记录，数字匹配仅说明来源链中有同值。
- 负责人、员工和卡片字段说明约定：汇报、卡片摘要、巡检说明、任务结果每条最多用一处 `**…**` 标出结论或关键数字。网页显示荧光底，保留未标文字的原貌。新放入的样例已标出摘要和汇报，摘要直接显示在项目标题下。已有项目和历史文字保持原样。
